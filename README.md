# webnovel-writer

面向 **单章 2000 字、可连续写数百至上千章** 的中文网文连载创作引擎。

一个 WorkBuddy / Claude Code Skill：把长篇连载从"每次对话从零开始"变成一套**可中断、可续写、不崩设定的工程化流水线**。

---

## 它解决什么问题

让 AI 写长篇，瓶颈从来不是文笔，是**记忆**和**纪律**：

| 症状 | 根因 | 本 skill 的解法 |
| --- | --- | --- |
| 写到第 300 章，设定前后矛盾 | 上下文装不下全书 | 分层记忆 L1-L7，每章只读约 15k 字 |
| 伏笔埋了忘了收，结局烂尾 | 没有账本，靠模型记忆 | 伏笔账本 + 强制回收期限（最多跨 2 卷） |
| 文风越写越飘，像换了个人 | 缺少风格锚点 | 从第 1 章提取「文风基准」，每章动笔前最后读 |
| 开局平淡，读者三章弃书 | 没有开局方法论 | 黄金三章专章设计 + 6 条「开局死法」清单 |
| 节奏拖沓、注水 | 无量化标准 | 2000 字微节奏模板 + 情绪标签调度 |
| 中断后接不上 | 无状态记录 | 两层状态机 JSON + `nextAction` 断点自动恢复 |
| 字数不达标还自评"约 2000 字" | 模型自评不可信 | 脚本实测（CJK 汉字 + 中文标点） |
| **连续六章全是压抑没爽点，没人发现** | **质量项无客观判据** | **`quality_check.py` 情绪节奏检查** |
| **钩子写法连用五章雷同，读者麻木** | **同上** | **`quality_check.py` 钩子形状轮换检查** |
| **章末全是软钩，读者没有点下一章的理由** | **只查"不连用"，不查强度** | **`quality_check.py` 软钩占比检查** |
| **前 14 章零收益，收益给在第 15 章——追读率早就掉了** | **门禁算不出开局空档** | **开局留存窗口 P0 + 「留存速览」** |
| **细纲说好要收的伏笔，写起来忘了** | **计划是自由文本，无从核对** | **`BATCH-DECLARATION` 声明块 + 执行率核对** |
| **口头豁免"前 8 章不改"，把改进建议一起吃掉了** | **豁免不入账** | **`waivers.json` 台账，每次体检打印** |
| 写长任务中途反复找用户确认 | Agent 行为退化 | 显式反退化禁令 + 重试上限 |

## 两个真实塌陷点（本项目为什么长这样）

这不是预想出来的功能清单，是在一部 39 章、7.3 万字的真实作品上跑出来的教训。

**塌陷一：规划与产出漂移。** 某批次细纲声明「强制回收」8 条伏笔，实际只执行 4 条，
另外 5 条是计划外推进——**声明执行率 50%**，而没有任何环节发现这件事。
根因：细纲是自由文本，没有被核对的结构。

**塌陷二：质量项全靠模型自评。** 除字数外，「情绪节奏 / 钩子轮换 / 连贯性 / 去 AI 味」
没有任何客观判据。于是「第 1-6 章连续 6 章无兑现」「钩子同形状连用 5 章」
这类 P0 问题安静躺了 39 章，直到人肉审稿才暴露。

**修复的方向是一致的：凡能确定性判定的，外移给脚本。**
模型的判断力应该花在「这段文字好不好」上，而不是给自己打勾。

## 核心设计

### 1. 三级规划，永远只为当前批次写细纲

```
总纲（7 卷骨架）
  └── 卷（30-80 章）· 卷级目标与卷末大事件
        └── 批次（默认 10 章）· 7 列细纲 + 情绪标签 ← 只在这一层写细节
              └── 单章（2000 字）
```

绝不为第 500 章之后写细纲——写完一批再规划下一批，规划精度不随篇幅衰减。

### 2. 分层记忆（千章规模的生存法则）

写第 N 章时，上下文中**只允许**出现这些：

| 层 | 内容 | 读取量 |
| --- | --- | --- |
| L1 | 上一章末 500 字原文 | 0.5k |
| L2 | 最近 3 章摘要 | 0.8k |
| L3 | 当前批次 7 列细纲 | 2k |
| L4 | 近 2 卷卷摘要 | 0.8k |
| L5 | 主线状态卡（主角实力/资源/关系/目标） | 0.5k |
| L6 | 伏笔账本相关条目 | 0.5k |
| L7 | 设定词典 + 总纲 | 视需要 |

**严禁重读全书旧章节全文。** 连贯性靠"每章回写 + 分层压缩 + 只读所需"，不靠"记住全部"。

### 3. 两层状态机 JSON

```jsonc
// 01-写作计划.json —— 书级索引，永不增长（<5KB）
{ "bookTitle": "...", "volumes": [...], "lastCompletedChapter": 12, "nextAction": "continue" }

// vol-01/计划.json —— 卷级状态机，只读当前卷
{ "volume": 1, "chapters": [ { "number": 1, "status": "completed", "wordCount": 2013, "emotionTag": "爽+燃" } ] }
```

单文件在千章规模下会膨胀到 200KB+，而每章都要读它——所以必须分层。
`nextAction` 让"继续更新"能自动判断：该写下一章 / 该补细纲 / 该卷归档 / 已完结。

### 4. 客观校验外移（三道防线）

**文件完整性**先兜底——头部丢了、正文整篇重复、混进 BOM/CRLF、章号缺号，这类问题
字数脚本和质量门禁都看不见，肉眼更难：

```bash
python "<SKILL_DIR>/scripts/manuscript_check.py" "<项目>/"              # 全书体检
python "<SKILL_DIR>/scripts/manuscript_check.py" "<项目>/" --json       # 有 ERROR 即非零退出
```

查七项：`head`（首行 `<!--` / 六个元信息键齐 / `# 第NNNN章 标题` 成形）、
`consistency`（文件名·头部·H1 三处章号一致）、`title`、`wordcount`、
`quotes`（配平 / ASCII 直引号 / 直角引号残留）、`encoding`（BOM / CRLF）、
`dup`（整篇重复）、`sequence`（缺号重号）。
**结构性损坏判 ERROR，字数不在区间只判 WARN**（老项目可能有"不达标但不修改"的约定）。

**字数**不靠模型自评，用脚本实测：

```bash
python "<SKILL_DIR>/scripts/check_wordcount.py" "<项目>/vol-01/第0001章-标题.md"
python "<SKILL_DIR>/scripts/check_wordcount.py" "<项目>/vol-01/"               # 整卷（直接传目录）
python "<SKILL_DIR>/scripts/check_wordcount.py" --all "<项目>/" --json         # 整本书 + 机器可读
```

计字口径 = CJK 汉字 + 中文标点（对齐主流网文平台）。默认达标区间 1700-2400，写作目标 2000。
HTML 注释中的章节元信息头不计入，且元信息自报字数与实测偏差超 50 字会告警。
支持一次传多个文件（旧版只认第一个、其余静默忽略）。

**质量纪律**同样外移——这是第三道防线，也是本 skill 区别于其他写作工具的地方：

```bash
python "<SKILL_DIR>/scripts/quality_check.py" "<项目>"                    # 全量体检（开头打印「留存速览」）
python "<SKILL_DIR>/scripts/quality_check.py" "<项目>" --chapters 45-45    # 单章门禁
python "<SKILL_DIR>/scripts/quality_check.py" "<项目>" --json --strict     # 有 P0 即非零退出
python "<SKILL_DIR>/scripts/selftest_quality_check.py"                    # 改过判定逻辑后必跑
```

| 检查 | 抓什么 | 级别 |
|------|--------|------|
| `emotion` | 连续「只有成本」超 2 章；兑现空档超 8 章（**从第 1 章起算**） | P0 |
| `emotion` | **开局留存窗口**：前 3 章兑现 <1、前 10 章兑现 <2 或收益 <3 | P0 |
| `emotion` | 情绪标签带模糊批注（`压(微爽:活下来)`） | P2 |
| `hook` | 章末钩子形状连用超 2 章 | P0 |
| `hook` | **软钩占比超 60%**（短句留白 / 对白悬停） | P1 |
| `ai_cliche` | 每千字 AI 腔高频词超 6 处 | P1 |
| `setting` | 词典外专有名词（须登记或确认同义混用） | P2 |
| `foreshadow` | 细纲声明的强制回收未执行 | P0 |

每条问题都带**章号 + 原句 + 触发规则 + 建议动作**。质量门禁嵌在 Phase 3 的每章循环里：
**P0 必须在本章内修掉**再进下一章，不得攒到批次末——问题要在产生当章暴露。

### 5. 网文方法论内置为可执行指令

不是"写作建议"，是**硬规则**：

- **黄金三章**：第 1 章命运改变之日 / 第 2 章金手指亮相 / 第 3 章第一个爽点兑现 + 分赛道变体
- **爽燃泪情绪曲线**：每章打情绪标签（爽/燃/泪/压），每 3-5 章一个小爽点、压两章必爆、泪点每卷 ≤2 次
- **2000 字微节奏**：300 字入冲突 → 1400 字推进 → 小高潮 → 钩子收尾
- **钩子十二式轮换**：同类钩子不连用两章（防读者麻木）
- **伏笔账本**：每条有 ID + 首现章 + 计划回收章，最多跨 2 卷强制回收
- **人物三段式**：主角每卷必须实质变化、配角记忆点三件套、反派三问（他要什么/为何有理/凭何威胁）

## 目录结构

```
webnovel-writer/
├── SKILL.md                          # 薄索引：四大铁律 + 阶段目录（按需加载其它文档）
├── references/
│   ├── flows/                        # 执行流程
│   │   ├── phase0-migration.md       #   手稿接入（既有作品挂载到本引擎）
│   │   ├── phase1-intake.md          #   创作立项（问答 / 总纲 / 力量体系 / 黄金三章）
│   │   ├── phase2-arc-planning.md    #   卷内细纲（批次规划 / 情绪曲线 / 伏笔排期）
│   │   ├── phase3-writing.md         #   逐章创作（写前分析→撰写→去AI味→校验→回写）
│   │   ├── phase4-validation.md      #   校验修复（六项检查 / 自动重写上限）
│   │   ├── phase5-review.md          #   审稿模式（对既有稿件体检，只读不改）
│   │   └── shared-infrastructure.md  #   共享机制（目录结构 / 记忆系统 / 状态机 / 偏好）
│   ├── guides/                       # 写作指南
│   │   ├── golden-three-chapters.md  #   黄金三章技法 + 开局死法清单
│   │   ├── emotion-and-pacing.md     #   爽燃泪配方 + 微节奏 + 钩子十二式
│   │   ├── characters-and-world.md   #   人物弧光 / 配角 / 反派 / 力量体系自洽
│   │   └── style-guide.md            #   去 AI 味 / 文笔辨识度 / 水字检测
│   └── templates/
│       └── chapter-template.md       # 章节文件模板（元信息头 + 写作纪律 + AI 腔清单）
└── scripts/
    ├── chapter_io.py                   # 章节文件解析/清洗的**唯一实现**（头部识别 + 正文清洗）
    ├── fix_punct.py                    # 标点归一化（半角→全角 / 直角引号 / ASCII 直引号）
    ├── fix_quotes.py                   # 中文引号按行配对修复
    ├── check_wordcount.py              # 字数检查（单章 / 多章 / 整卷 / 整本书 / JSON）
    ├── quality_check.py                # 质量门禁（留存/情绪/钩子强度与轮换/AI腔/设定/伏笔执行率）
    ├── selftest_quality_check.py       # 门禁自身的反向验证（坏样本必须报红）
    ├── manuscript_check.py             # 全书体检（头部/编码/重复/配平/章号连续性）
    ├── split_chapters.py               # 逐章 md → 可直接粘贴的纯文本分章 + 分卷合并稿
    ├── delivery_check.py               # 交付终检（成品 vs 源文件逐字比对 + 上架门槛）
    └── make_cover.py                   # AI 底图 + 矢量文字合成 600×800 投稿封面
```

> **为什么有 `chapter_io.py`**：章节文件以 `<!-- 元信息块 -->` 开头，而多个脚本曾各自用
> `re.match(r"^#...")` 抓标题——`re.match` 只锚定字符串开头，对这类文件**永远匹配不上**，
> 导致元信息块泄进成品、标题塌成「第一章」，而终检因为两端用的是同一套坏逻辑反而报「一致 ✅」。
> 现在解析与清洗**只有一个实现**，所有脚本 import 它。

**渐进式加载**：SKILL.md 是索引，详细指令全在 references 下按需读取——既不爆上下文，又保证执行时指令的细粒度。

| 场景 | 说法 |
| --- | --- |
| 开新书 | 「用 webnovel-writer 写一本修仙小说」 |

## 设计取舍与已知局限

- **语义判断仍归模型**：脚本能判定「是否违反已写死的纪律」，判断不了「这段文字好不好」。
  黄金三章是否达标、人物是否立体、名场面是否成立，这些仍需模型带原文证据来论证。
- **质量脚本的阈值是按中文网文校准的**（连续压 ≤2 章、爽点间隔 ≤8 章、钩子连用 ≤2 章）。
  改写其他体例（文学长篇、剧本）需在脚本 `RULES` 中重新定标。
- **并行写作模式下**，子批次依赖批次前的统一大纲，跨批次伏笔仍有失控风险——所以默认串行，并行需显式开启。
- **用户偏好存于本地 JSON**（`user-preferences.json`），不跨设备同步。
- 默认面向**中文网文**：计字口径、情绪配方、钩子技法都按中文网文生态校准。
- Skill 不能替代作者的判断：它保证"不崩、不断、不注水、不塌陷"，不保证"好看"。
