# Phase 3: 逐章创作

**进入本阶段后全程禁止向用户确认，写完当前批次（连载模式下写完本次请求的批次量）才能汇报。**

## 0. 启动检测

1. 读根 `01-写作计划.json` → 取 `nextAction`、`lastCompletedChapter`、当前卷号。
2. 读当前卷 `vol-XX/计划.json` → 确定下一待创作章节（`in_progress` 半成品重写 / `failed` 重写 / 首个 `pending`）。
3. 读 `02-主线状态卡.md` 与当前批次细纲。若当前批次无细纲 → 先执行 Phase 2。

## 1. 写前分析（每章必做，顺序固定）

1. 读 `vol-XX/卷细纲.md` 本章行：核心事件、关键场景、情绪标签、钩子设计、伏笔操作、出场人物、小爽点位置。
2. 读 `04-设定词典.md`：核对本章设定名词（首现名词需给上下文线索；已介绍名词表述不得超出词典范围）。词典过大时只读本章相关条目。
3. 读 `03-伏笔账本.md` 中本章涉及的埋设/兑现/推进条目原文。
4. 读 `02-主线状态卡.md`：主角当前实力、资源、关系、位置，禁止出现状态卡之外的"凭空能力"。
5. 读上一章**章末 500 字原文** + `vol-XX/章节摘要.md` 末尾 3 条（最近 3 章摘要）。
6. 写第 1-3 章时：先读 `references/guides/golden-three-chapters.md`；写第一卷任意章时读 `05-文风基准.md`（首卷首章时该文件为空，写完后回填）。
7. 更新卷级 JSON：本章 `status` → `"in_progress"`。

> **动笔前最后读到的必须是正文语态文字（上一章章末 + 文风基准），不要让表格成为最后上下文。**

## 2. 撰写（目标 2000 字，写作区间 1800-2200）

章节文件：`vol-XX/第%04d章-{标题}.md`（标题来自卷级 JSON 的 `title`），文件头写元信息（章号/标题/情绪标签/伏笔操作），正文用 `references/templates/chapter-template.md` 的结构。

- **开头 300 字内进入冲突或钩子**，背景交代以"遭遇"呈现，禁止静态介绍
- **中段执行情绪标签**：按细纲主情绪设计本章核心节拍，副节拍穿插；连续 500 字无冲突必须引入新张力
- **小爽点兑现**：按细纲位置落实（打脸/升级/收获/反转），兑现前先给足"压抑/蓄力"半拍
- **对话 ≥ 30%**：每段对话必须有潜台词或推进情节；对话风格严格符合人物设定
- **伏笔操作**：按细纲执行埋/推/收，埋设时自然融入场景，不得生硬
- **记忆点尝试**：每章至少一个可被读者记住的元素（金句、名场面、反转、人物高光）
- **结尾钩子**：按细纲的钩子设计执行，章末必须留下未解决张力；钩子类型不得与前两章连续重复
- **力量体系红线**：升级必须有代价/条件；越级表现必须有前文铺垫；禁止使用词典外的能力名词

## 3. 润色去 AI 味（对照 `references/guides/style-guide.md`）

- 删除四字成语堆砌与过度修饰词
- 抽象情绪陈述改为具体动作/对话/细节
- 长短句交替，强化节奏感
- 对话口语化、个性化，删掉"正确的废话"
- 逐段自问"删掉这段情节是否受损"，无损即删（2000 字经不起注水）

## 4. 校验与回写

### 4.1 脚本校验（先客观，后主观）

**字数**（必须，每章）：
```bash
python "<SKILL_DIR>/scripts/check_wordcount.py" "vol-XX/第0001章-标题.md"
```
低于 1700 字 → 回步骤 2 扩充；高于 2400 字 → 删水。

**文件完整性**（每批次末必跑，不是每章）：
```bash
python "<SKILL_DIR>/scripts/manuscript_check.py" "<项目>/"
```
查头部（首行 `<!--`、六键齐、`# 第N章 标题` 成形）、三处章号一致、字数漂移、
引号配平、BOM/CRLF、整篇重复、章号缺号。
> 这一项**以前漏在流程外**，实测让第 7 章的头部丢失一路活到交付。**批次不跑它 = 没资格收尾。**

**质量门禁**（必须，每章写完立即跑）：
```bash
python "<SKILL_DIR>/scripts/quality_check.py" "<项目>" --chapters <本章号>-<本章号>
```
本脚本检查五项**可计算**的质量纪律，结果带章号证据：

| 检查 | 抓什么 | 违规处置 |
|------|--------|----------|
| `emotion` | 连续「压」超 2 章、爽点间距超 8 章 | 本章改为兑现章（打脸/升级/收获） |
| `hook` | 章末钩子形状与前章连用超 2 章 | 换钩子类型（钩子十二式） |
| `ai_cliche` | 每千字 AI 腔高频词超 6 处 | 按 style-guide 润色步骤 1 删病灶 |
| `setting` | 词典外专有名词 | 确认是新设定则登记词典 |
| `foreshadow` | 细纲声明的伏笔动作未执行（仅批次末触发） | 补写或改期 |

**判定为 P0 的，必须在本章内修掉再进入下一章**——这是本 skill 反「质量塌陷」的核心机制：
质量问题必须在**产生当章**暴露，不得攒到批次末或靠读者反馈。
不得用「下一章再补」作为理由跳过 P0；如果确实要顺延，必须在细纲中显式改期。

> ⚠️ **不要用模型自评替代脚本。** 实测一部实战验证作品第 1-39 章：模型自评「节奏紧凑、钩子到位」，
> 脚本实测出「第 1-6 章连续 6 章无兑现」「第 9-13 章钩子同形状连用 5 章」两项 P0。
> **凡脚本能算的，一律以脚本为准。**

### 4.2 主观自检三问（脚本覆盖不到的部分）

脚本只能验证纪律，不能判断「好不好看」。以下三项仍需模型判断，但必须**给出具体证据**才算通过：
1. 钩子留下了吗？——指出本章末句，说明它制造的是什么张力。
2. 情绪标签兑现了吗？——指出承载情绪的那一段（哪几句、什么手法）。
3. 主线三问在章末依然清晰吗？——一句话答出「主角要什么/阻碍是什么/下一步是什么」。

### 4.3 回写记忆（一步不可省）

- **章摘要**（150-250 字）追加到 `vol-XX/章节摘要.md`
- **伏笔账本**：新埋条目登记；兑现条目结清；推进条目更新状态
- **主线状态卡**：实力/资源/关系/位置/目标如有变化立即更新
- **设定词典**：本章首现设定名词登记
- **卷级 JSON**：`status → "completed"`，填 `wordCount`、`emotionTag`
- **根索引**：更新 `lastCompletedChapter`、`totalCompletedChapters`、当前卷 `completedChapters`
- **钩子形状**（新增，供轮换检查）：在卷级 JSON 该章条目补 `hookShape` 字段，
  取值见 `quality_check.py` 的 `hook_shape()`。**不填会导致下一章的轮换检查失准。**
- **情绪标签必须用受控词表**：`压` / `泪` / `秘辛` / `爽` / `燃` / `暖`，可组合（`压+泪`）。
  **不要写批注**（`压(微爽:活下来)` 这种不作数，脚本会单列一条 P2 点名它）——
  全部留存判定都建立在这张表上，标签含糊 = 判定含糊。

> 🔴 **第 3 章与第 10 章写完，必须各跑一次留存门禁**，不要等到批次末：
> `python "<SKILL_DIR>/scripts/quality_check.py" "<项目>"`
> 看开头的「留存速览」——前 3 章兑现 ≥1、前 10 章兑现 ≥2。这两处是平台追读率的
> 判定窗口，**过了就补不回来了**；开局缺的收益，后面写得再好也换不回已经走掉的读者。

> ⚠️ **伏笔动作必须与细纲对齐**：本章埋/推/收了哪些伏笔，必须与 `卷细纲.md` 该章
> 「伏笔操作」列一致。若实际写作偏离了细纲（写出来发现更好的处理方式），
> **必须同步修改细纲该行**，否则批次末的质量门禁会报 `foreshadow` 违规，
> 且下批次的伏笔排期会算错。
> 实测教训：一部实战验证作品批次 4 细纲声明强制回收 8 条，实际只执行 4 条，另外 5 条是计划外推进——
> 声明执行率仅 50%，且没有任何环节发现这件事。

## 5. 自驱循环与批次推进

```
WHILE 本批次存在 status != "completed" 的章节:
    执行步骤 1-4，完成一章立即认领下一章，不询问、不停顿
本批次完成 → 执行 Phase 4 校验 → 生成批次摘要（150字）写入卷细纲的批次摘要区
           → 报告批次进度（各章字数+情绪标签一览）
若本卷还有未细化批次 → 执行 Phase 2 细化下一批次 → 继续循环
若本卷写完 → 执行 Phase 2 的卷末归档 → 询问用户是否继续下一卷
```

> 关键提醒（每章完成后默念）：不要使用 AskUserQuestion，不要中途汇报，把当前批次写完。

## 6. 可选：并行写作模式

仅当用户明确要求提速、且单批次 ≥ 8 章时使用（默认串行，最稳定）。

- **批次切分**：按 5-8 章切分为不重叠的连续子批次，每个子批次派一个子 Agent（同一条消息内并行派发）。
- **无冲突保证**：状态拆分后天然隔离——每个子 Agent 只写自己子批次的章节文件、只改自己子批次的 JSON 条目与摘要；`03-伏笔账本.md`、`02-主线状态卡.md`、`04-设定词典.md` 为共享写文件，**禁止子 Agent 直接改**。
- **主 Agent 收口**：所有子 Agent 返回后，由主 Agent 统一合并：先把各子批次新增的伏笔条目登记入账本、状态卡更新为主角在该批次末尾的最终状态、设定词典补登记；随后执行 Phase 4 校验。
- **风险与规避**：并行会导致跨子批次的伏笔埋收断裂、主线状态卡中间态丢失 → 因此子批次切分点必须落在"情绪标签为压/铺垫"的章之后，不得切在爽点兑现章中间；子 Agent 的 prompt 中必须给出该子批次的"起点状态快照"（从主线状态卡摘取）。
